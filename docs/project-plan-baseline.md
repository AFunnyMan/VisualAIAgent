# AI 视觉智能体：开发路线、Codex 工作流程与项目文档计划

## 1. 目标与执行原则

在 `/Users/fanxinhao/project/VisualAIAgent` 开发兼容 Mac 和 Windows 的视觉记忆智能体：

- 普通 USB 摄像头持续识别手机、杯子、瓶子。
- 保存物品最后出现的时间、画面位置和截图。
- **AI Agent 为首版正式模块**，支持自然语言查询、创建关注任务、取消任务和事件触发提醒。
- 持续观察全部在本地完成；云端只处理必要的文字请求。
- 首轮以无独显、8GB 内存电脑为验收基线。

技术组合确定为：

**Python 3.11 + OpenCV + YOLO26n ONNX + ONNX Runtime CPU + Supervision + SQLite + OpenAI Agents SDK + Streamlit。**

直接复用 Agents SDK 的执行循环和工具调用、Supervision 的检测结果处理与绘制、YOLO 的预训练模型；Frigate 作为事件处理设计参考，不整套移植。

采用你选定的执行节奏：**开始实施后，Codex 在每个阶段验证通过、记录证据后连续推进。** 若缺少 API 配置或 Windows 实机，继续完成不依赖它们的工作，将对应验收明确保留为未完成。

当前目录为空、尚未初始化 Git。本轮只完善计划，下面列出的文件均在实施阶段创建。

## 2. 项目文档如何创建和维护

参考指定文档，将“目标、计划、实际进展”分别保存。官方明确指出，AGENTS.md 是 Codex 识别的指引文件，其余名称属于可调整的工作流约定。[开发工作流文档](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex)

**第一步：创建工作约定和产品目标。**

- **AGENTS.md**：写入项目简介、文档读取顺序、代码与验证约定、连续推进规则。突出“Agent 必须真实调用工具”“不上传视频”“不把摄像头故障判成物品消失”等长期约束。保持简短，通过链接引导阅读详细文档。
- **GOALS.md**：以本次对话中的明确选择为依据，记录目标用户、首版功能、成本要求、不做的功能和验收条件。为需求分配编号，例如 G01 本地识别、G02 视觉记忆、G03 Agent 查询、G04 关注提醒、G05 成本控制、G06 双平台。
- 新建 AGENTS.md 后，在当前实施会话中显式读取一次；后续任务启动时再按 Codex 的规则发现它。[AGENTS.md 官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

**第二步：创建路线图和技术约定。**

- **PLANS.md**：保存本计划确定的阶段顺序、依赖关系、推进条件和阶段文档索引，不复制执行日志。
- **architecture.md**：保存模块关系、数据流、Agent 工具接口、事件与任务状态、线程职责、持久化和故障处理。
- **testing.md**：记录测试分层、执行入口、测试数据、人工摄像头验证步骤及平台验收矩阵。
- **references.md**：记录实际采用的官方文档和开源项目，包括 URL、查阅日期、复用用途、许可证、选定版本或提交及本项目的调整。只保存必要摘要，不复制整篇文档。

**第三步：创建各阶段执行计划。**

每个阶段文档必须说明：

1. 对应哪些需求，用户完成后能看到什么变化。
2. 前置条件、涉及模块、接口和明确边界。
3. 具体实施步骤、检查命令及预期行为。
4. 验收条件、异常场景、重复执行和恢复方法。
5. 当前进度，以及相关决策、证据和下一步的链接。

借鉴 ExecPlan 的“持续更新、可从文件恢复工作、以可观察行为验收”方法。该文章已归档，因此不继承其旧模型或 API 推荐。[ExecPlan 文档](https://developers.openai.com/cookbook/articles/codex_exec_plans)

**第四步：创建操作入口和记录容器。**

- **PROMPTS.md**：提供六种简短入口——了解项目、准备阶段、实施阶段、验证、修复审查问题、恢复工作。每种入口指定应读文档、任务范围和完成证据，避免重复产品需求。
- **build-log.md**：初始化阶段状态，初始均为“未开始”；后续记录实际执行和结果。
- **context**：只在某阶段开始后创建该阶段的上下文文件，保存影响后续工作的发现、取舍和未解决条件，不预填“已完成”内容。
- **code_review**：在实际审查时创建记录。
- **artifacts**：保存必要测试输出与报告；运行截图、数据库、密钥和大文件不进入版本控制。
- **README.md**：最初标明“开发中”，随着真实功能完成补充安装、启动和演示步骤。

文件职责保持清楚：目标归目标文档，技术接口归架构文档，阶段步骤归阶段计划，实际结果归日志。其他位置只引用，避免多份副本逐渐矛盾。

## 3. 分阶段实施过程

| 阶段 | 实施内容 | 可观察的交付与验收 |
|---|---|---|
| **00：项目基础** | 创建上述文档；初始化本地 Git；建立 Python 项目、依赖管理、忽略规则和示例配置 | 所有需求都有对应阶段；开发环境可安装；文档中的现状与空项目一致 |
| **01：Agent 核心** | 接入 Agents SDK；定义工具接口；用明确标记的模拟视觉数据验证查询、创建及取消任务 | 页面或开发入口可展示工具名称、参数和结果；真实 API 测试与模拟测试分别记录 |
| **02：本地视觉** | 接入摄像头、YOLO26n ONNX、CPU 推理、Supervision 绘制和画面区域 | 能观察三类物品及其位置；提供实际推理耗时；摄像头断开显示异常 |
| **03：视觉记忆** | 实现事件确认、SQLite、截图、最后出现查询和保留策略 | 拿走手机后仍可查询最后观察证据；重启后历史存在；短暂遮挡不过早触发事件 |
| **04：事件驱动 Agent** | 将关注任务持久化；连接事件匹配、Agent 唤醒、状态复查和提醒工具 | 自然语言建立任务后可等待并自动提醒；无事件时不调用模型；重复事件不重复提醒 |
| **05：用户界面** | 整合实时画面、聊天、时间线、任务列表、证据和用量显示 | 用户能在一个本地页面完成“识别—查询—关注—提醒—取消”演示 |
| **06：验证与交接** | 回归测试、真实 Agent 验证、双平台运行、性能记录、审查和使用文档 | 交付可重复演示的源码版本、启动脚本、验收报告和明确的未验证项 |

**阶段 01 的模拟数据只用于验证接口和执行流程，阶段 03 必须替换为真实视觉记忆。** 无真实模型凭据时可以继续开发，但不能宣称 Agent 端到端验收已通过。

**需要在架构文档中固定的接口**

Agent 保留七个工具：读取当前场景、查找物品、搜索事件、创建关注、列出关注、取消关注、显示提醒。

统一定义检测结果、场景观察、视觉事件、关注任务和工具执行结果的数据类型。每次工具返回包含成功状态、数据或错误；视觉事实包含时间和证据引用。

关注任务支持“出现”和“持续未检测到”，默认三十分钟、成功提醒一次后完成；状态为等待、处理中、完成、取消或过期。同一任务与事件只能形成一条有效提醒。

**运行行为默认值**

- 摄像头请求 640×480；保持比例填充到模型输入尺寸；每秒识别一次，预览每秒更新两次。
- 连续三次检测确认出现；有效画面中连续五秒未检测到后形成事件。
- 按画面左、中、右记录位置；多个同类物品展示候选，不推断身份。
- 摄像头故障或暂停时停止物品缺失计时；重启不推断停机期间发生的事件。
- 普通事件截图保留七天，另保留每类物品最后观察证据。
- Agent 请求使用独立队列，不阻塞视觉处理；超时或失败时保留本地事件提醒，明确记录 Agent 未完成。

## 4. Codex 每个阶段如何工作

执行循环固定为：

**读取现场 → 确认本阶段目标 → 实现最小完整功能 → 验证 → 审查修复 → 更新记录 → 推进下一阶段。**

具体要求写入 AGENTS.md 和 PROMPTS.md：

- **先核对现场。** 读取适用指引、目标、当前阶段计划和最近日志，再检查相关代码。不能仅凭上一次聊天中的“已完成”判断现状。
- **先解决关键不确定性。** 摄像头访问、ONNX 输出格式、模型工具调用兼容性优先做小规模验证，成功后再扩展。
- **有针对性地测试。** 事件状态机、任务去重、超时恢复等核心行为采用先失败再通过的测试；文档和简单界面改动不强制编写形式化测试。
- **完成后检查整个行为。** 不以“文件已创建”或“程序能启动”作为功能完成依据。
- **记录真实结果。** 日志包含时间与时区、阶段、实际命令、退出状态、关键结果、证据位置、限制和下一步。失败与跳过的验证保留记录，纠错以追加说明处理。
- **及时更新决策。** 若实测改变阈值、依赖或接口，同步更新负责该信息的文档，并记录原因；不自动降低产品验收标准来获得通过。
- **按已授权范围连续推进。** 阶段验证通过后直接进入下一个阶段；涉及产品范围变化或必要条件缺失时，明确提出具体问题，并继续可独立完成的工作。
- **结束或中断前留下恢复点。** 写清当前状态、最后通过的检查、尚未解决的问题和下一条可执行动作。

首版不为文档流程额外开发复杂自动化平台，也不修改全局 Codex 设置。先通过项目文档验证流程有效；项目复盘中再记录哪些重复操作值得沉淀为可复用 Skill。

本地 Git 用于检查变更范围；本计划不包含自动提交、推送或发布远程仓库。

## 5. 验证体系、成本与最终完成条件

**验证分为三层。**

| 层次 | 验证内容 | 证据 |
|---|---|---|
| 离线自动测试 | 状态转换、数据库、工具参数、任务去重、取消、过期、恢复、模型调用限额 | 测试输出和失败案例 |
| 真实模型测试 | 模型实际选择工具、读取结果、创建任务及生成有依据的回答 | 模型名称、调用记录、Token 用量、工具执行结果 |
| 摄像头与平台测试 | 真实物品放入／移出、遮挡、断开、双平台安装与持续运行 | 环境信息、操作步骤、时间数据、截图或报告 |

拟采用以下检查入口；这些是**实施时需要建立并验证的命令，不是现有命令或已通过的结果**：

```text
uv sync --locked --group dev
uv run ruff check .
uv run pytest -m "not live_api and not camera"
uv run pytest -m live_api
uv run streamlit run app.py
git diff --check
```

测试配置显式区分 `live_api` 和 `camera`，默认测试不调用付费模型、不打开摄像头。实时摄像头效果另按使用文档执行人工验证。

**必须覆盖的验收场景**

- “手机最后在哪里出现？”调用查询工具，返回时间、区域和证据；未知物品不编造答案。
- “关注手机半小时”实际创建任务，“取消刚才的关注”实际取消。
- 等待十分钟、没有匹配事件时，模型调用次数不增加。
- 持续未检测到后触发 Agent，复查状态并提醒；重复投递不重复提醒。
- 遮挡两秒、摄像头断开、暂停和重启不产生错误的物品消失结论。
- 同类物品多个时展示候选，不冒充物品身份识别。
- API 超时、非法工具参数、数据库错误能被准确记录和反馈。
- Mac 与 Windows 分别持续运行三十分钟，记录 CPU、内存、推理耗时和提醒延迟。
- 固定光照、无遮挡条件下，三类物品各执行十次放入／移出，事件正确率目标至少 90%，同时保留失败样例。

**成本默认值**

每次 Agent 运行最多三轮模型调用，关闭自动网络重试；每次检索最多二十条事件，会话携带最近五个完整交互。自动事件每天最多触发二十次 Agent 运行，达到上限后继续本地提醒。图片和视频不上传，实际 Token 以提供商返回值记录。

模型通过 API 地址、明确模型名称和环境变量 Key 配置，不暗用 SDK 的默认模型。缺少配置时标记“Agent 未连接”，不能拿模拟执行作为真实模型证据。

**最终交付**

源码、锁定依赖、模型来源与校验信息、双平台启动脚本、上述项目文档、阶段审查记录、验收报告和演示步骤。

只有产品行为和必需验证均有证据时，才能将项目标记完成。Windows 实机或真实 API 验证缺失时，交付中保留具体待验证项；所有阶段结束后进行一次复盘，将已验证的经验写回项目指引或回归测试。
